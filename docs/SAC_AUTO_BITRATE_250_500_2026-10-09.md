# DAF SAC — automatic 250/500 kbit/s identification (2026-10-09)

Branch: `webgui/sac-local-prototype-no-token-20261009`.
Hardware lab workflow: operator selects TESTY → TRUCK → DAF → SAC.
No new UI control, no extra user interaction.

## Connection algorithm

1. Refuse if can0 is already UP (protect other sessions).
2. Configure CAN Classic normal 250,000 bit/s; launch root-installed,
   allowlisted UDS read-only binary as unprivileged `ecu`.
3. **Only** positive ISO-TP/UDS identification of DID F190 (VIN),
   F188 (software) and F192 (hardware) is proof of communication.
   `FF × 17` is an explicitly reported *unprogrammed VIN*, not a reason
   for failure if SW/HW and the UDS positive results are valid.
4. If **no response or identification timeout**, ensure CAN DOWN, then
   configure CAN Classic normal 500,000 bit/s and repeat once. If the
   250 kbit/s exchange succeeded, do not probe 500.
5. Wrong or ambiguous **positive** payload/identity fields abort
   (no fallback that could mask an inconsistent response). Link errors
   and inability to bring CAN DOWN abort. Never use presence/absence of
   ACK or passive broadcast traffic as the acceptance criterion.
6. On the first successful identification, use the **same speed** for
   the completed read-only SAC parameters probe. Select corresponding
   `profile_id`: `0xDAF00025` for 250k, `0xDAF00050` for 500k.
   An unavailable pressure remains null, not 0 bar.
7. Always bring CAN DOWN on exit, including errors.
   Unknown results are never represented as a successful connection.

The GUI shows a centered "Komunikacja…" spinner, then VIN/SW/HW and
the negotiated bitrate. "OK" advances to the historical parameters
screen only after positive identification. A fully failed attempt
shows "Błąd komunikacji" with Retry / Back.

Existing low-level probe binaries support both bitrates; the
root-installed filenames contain `500k` only for legacy packaging
reasons. This change updates only the Linux-specific read-only
application adapter, its HTTP response DTO, the browser-side validation
and the two-speed identity label. CORE and Bench Runtime are unchanged.

## Tests and installation

Regression tests use mocked CAN link operations and probe outputs (never
touch real hardware). They cover:
- positive first 250k with no 500k transmission,
- missing 250k response followed by positive 500k,
- CAN DOWN between attempts and after completion,
- aborted fallback for malformed positive identification,
- mapping 250k and 500k to the correct DUT profile,
- browser-side rejection of inconsistent bitrate/profile pairs,
- previous no-token kiosk and authenticated read-only API tests,
- scoped installer refusal for unprivileged users and rollback.

The CM5 is currently running the proven earlier GUI version
`e62d4d1d4d93` and adapter SHA
`5e523611979fecf6468eb02c62b19304f408fb6df0f8451834e13848a2e2a8e7`.
Install this candidate after CI review using a single atomic
operator-only staged cutover:

```bash
cd ~/ECU_WEBGUI_PARAMS_V1
sudo bash scripts/deploy_cm5_sac_dual_bitrate.sh
```

The installer checks expected current releases, services and can0 DOWN,
backs up the old adapter and GUI link, installs a new immutable static
release and backend, restarts only SAC adapter + static GUI + kiosk, and
checks health **without sending UDS**. On error it rolls back.

Recovery:
```bash
sudo /usr/local/sbin/ecu-sac-dual-bitrate-rollback
```

**Physical acceptance**: With the already attached known 500k SAC,
press SAC once, confirm fallback from 250 to 500 and displayed 500k
SW/HW and completed parameters after OK. A 250k SAC (if available)
requires a separate positive test; do not claim 250k hardware PASS solely
from simulated unit tests.
